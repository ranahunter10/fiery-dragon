# P15W v1.0: write-ahead log segment format

Normative for the writer (`daemon/wal.c`) and every reader. Implements ADR-0007; records inside batches are those of ADR-0008. A change to anything below is a new format version: readers keep every old version forever.

All integers are **little-endian**. All offsets are in bytes. "CRC32C" is CRC-32/ISCSI (Castagnoli polynomial `0x1EDC6F41`, reflected `0x82F63B78`, initial value and final XOR `0xFFFFFFFF`). Its check value for the ASCII bytes `123456789` is `0xE3069283`.

## 1. Files

- One run per directory: `<wal-root>/<run-id>/`.
- Segments: `seg-<index>.p15w`, where `<index>` is 8 decimal digits from `00000000`, contiguous within a run.
- A segment is: **header**, then zero or more **batches**, back to back, to the end of the file.

## 2. Segment header

### 2.1 Fixed prefix (32 bytes)

| Offset | Type | Field | Value |
|---|---|---|---|
| 0 | u8[4] | `magic` | `P15W` |
| 4 | u16 | `major` | 1 |
| 6 | u16 | `minor` | 0 |
| 8 | u32 | `byte_order` | `0x01020304` (the bytes `04 03 02 01`) |
| 12 | u32 | `header_len` | whole header, prefix included; a multiple of 8 |
| 16 | u32 | `header_crc` | CRC32C of the whole header with this field read as 0 |
| 20 | u32 | `segment_index` | equals the index in the file name |
| 24 | u32 | `meta_count` | number of metadata entries that follow |
| 28 | u32 | reserved | 0 |

### 2.2 Metadata entries (`meta_count` of them, from offset 32)

| Offset | Type | Field |
|---|---|---|
| 0 | u16 | `key_len`, 1–255 |
| 2 | u16 | reserved, 0 |
| 4 | u32 | `value_len`, ≤ 65,536 |
| 8 | u8[`key_len`] | key: `[a-z0-9._-]` |
| … | u8[`value_len`] | value: UTF-8 text (numbers in decimal) |
| … | | zero padding to a multiple of 8 |

The entries end exactly at `header_len`. Keys are unique within a header.

**Written by the writer in every segment:**

| Key | Meaning |
|---|---|
| `clock.boottime_ns`, `clock.monotonic_ns`, `clock.realtime_ns` | clocks read back to back at segment open (L5) |
| `clock.read_spread_ns` | boottime after the three reads minus boottime before them |
| `seq.next.spine`, `seq.next.bulk`, `seq.next.daemon` | the sequence number the next batch of each ring starts at (§3.2) |
| `rotate.max_bytes`, `rotate.max_ms`, `sync.interval_ms` | rotation and durability settings (ADR-0007 rules 1, 6) |

**Written by the daemon in every segment** (passed through the writer, step 4b): run id, `boot_id`, hostname, kernel release, schema hash, daemon commit, libbpf and bpftool versions, the hook manifest and self-test result, ring sizes, timezone, and bytes cut from a torn tail on recovery. Their key names are listed with the daemon.

## 3. Batches

### 3.1 Batch header (40 bytes, at an offset that is a multiple of 8)

| Offset | Type | Field | Rule |
|---|---|---|---|
| 0 | u8[4] | `magic` | `P15B` |
| 4 | u16 | `ring` | 0 spine, 1 bulk, 2 daemon |
| 6 | u16 | `flags` | 0 |
| 8 | u32 | `count` | ≥ 1 |
| 12 | u32 | `payload_len` | a multiple of 8, ≥ 32 × `count`, ≤ 16 MiB |
| 16 | u64 | `first_seq` | §3.2 |
| 24 | u32 | `payload_crc` | CRC32C of the payload |
| 28 | u32 | reserved | 0 |
| 32 | u32 | `header_crc` | CRC32C of bytes 0–31 of this header |
| 36 | u32 | reserved | 0 |

The payload follows: `count` records of ADR-0008, each starting with its 32-byte header. A record's `len` (u16 at record offset 4) is ≥ 32 and a multiple of 8. The records tile the payload exactly: their `len`s sum to `payload_len`.

One batch is written with one `writev` (ADR-0007 rule 4). All records in a batch come from one ring.

### 3.2 Sequence numbers

Each ring has its own u64 sequence, starting at 0 for a run. Record *i* (from 0) of a batch has sequence `first_seq + i`. Within a run, for each ring, each batch's `first_seq` equals the previous batch's `first_seq + count`, across segment boundaries too. Each segment header's `seq.next.<ring>` equals the next `first_seq` of that ring.

## 4. Reading, torn tails and recovery

A reader walks the batches from `header_len` and stops at the **first** batch for which any of the following holds:

1. fewer than 40 bytes remain;
2. wrong `magic`;
3. `header_crc` does not match;
4. a reserved field or `flags` is not 0, or `ring` is not 0–2;
5. `count` or `payload_len` breaks §3.1;
6. `payload_len` is larger than the bytes remaining;
7. `payload_crc` does not match;
8. the records do not tile the payload, or their number is not `count`;
9. `first_seq` breaks §3.2.

A stop is a **torn tail**, what a write cut short by a crash looks like, when:
- the cause is 1 or 6; or
- the cause is 7 and the batch ends exactly at the end of the file; or
- every byte from the stop to the end of the file is zero (a file system can leave a zero-filled tail after a crash).

Everything before the stop is valid. Everything from the stop on is not data and is never decoded.

- **Recovery (writer, on restart):** truncate the segment at the stop, and count the bytes cut. The daemon writes that count in the next segment's header.
- Any stop that is not at a torn tail (a CRC failure followed by more bytes, or cause 9) is **corruption**. It is reported, never truncated silently.

A segment whose header fails its checks (magic, version, byte order, length, CRC, metadata entries, a missing `seq.next.<ring>`) is not read at all. Recovery never truncates such a segment, including one cut short inside its header: that is reported for a person to decide.

## 5. Durability

The writer calls `fdatasync` on the segment at each rotation, at close, and when at least `sync.interval_ms` (default 1,000) has passed since the last sync and bytes were written since. After creating a segment it calls `fsync` on the run directory, so the new file's name is durable too. A power loss therefore loses at most about one interval of records (ADR-0007 rule 6).

## 6. Rotation

A new segment starts:
- before a batch that would take the segment past `rotate.max_bytes` (default 64 MiB), unless the segment holds no batch yet. A batch larger than the limit goes alone into a segment, and it is counted;
- when `rotate.max_ms` (default 60,000) has passed since the segment opened and it holds at least one batch.
